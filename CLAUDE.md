# Working conventions

Project-specific rules for AI assistants. Detail lives in `CONTRIBUTING.md` (how to
contribute) and `dev-docs/` (maintainer notes, local-only); this file is only the
things that are easy to get wrong.

## Git

- **Work directly on `main`.** No feature branches, no pull requests — this is a
  single-maintainer project and the PR ceremony buys nothing here. (The two PRs in
  the history are not the convention.)
- **Never commit or push without asking first.** Prepare the change, run the checks,
  then ask.
- `CONTRIBUTING.md` still tells *outside* contributors to branch and open a PR. That
  is correct for them — they cannot push to `main`. Do not "fix" it to match this
  file.

## Before a tag

Three generated artefacts must be in sync, and CI fails on each:

```bash
python3 -m unittest discover -s tests            # 201 tests, no network, no Zotero
uv run --with pymupdf python -m unittest discover -s tests   # the other 18
uvx ruff check src tests cli/zot scripts
python3 scripts/gen_cli_reference.py             # then: git diff --exit-code
python3 scripts/gen_updates_json.py --check      # the plugin's auto-update manifest
python3 scripts/gen_homebrew_formula.py --check  # the Homebrew formula
```

The release itself is tag-driven (`git tag vX.Y.Z && git push --follow-tags`), and it
ends with one manual step: `gh workflow run sync.yml --repo alex-roc/homebrew-tap`.
See `CONTRIBUTING.md` → "Cutting a release".

Run the suite **both ways**. Without PyMuPDF installed, 18 engine-dependent tests
in `test_toc.py` report as `skipped` — and CI's `test-toc` job installs the extra
and runs them for real. Refactoring `commands/toc.py` and reading a local "OK
(skipped=18)" as a pass is how v0.7.0 shipped a tag whose CI was red: the tests
patched a symbol (`toc.pdf_paths`) that the refactor had moved.

`gen_updates_json.py` can only fill in `update_hash` when the built XPI is at hand,
so **running it locally silently drops the hash** — the value in `updates.json` comes
from CI. Never commit the local output as a way of "fixing" the manifest; restore the
file from the commit that last announced that version instead.

## Rewriting published history

Because the release is tag-driven, **force-pushing a tag re-runs the whole Release
workflow** for it — which re-uploads assets, re-appends the autogenerated notes to
the existing release body, and pushes a `release: announce vX.Y.Z` commit to `main`.
With several tags pushed at once they race, and an *older* tag can win and leave
`updates.json` offering a downgrade to every installed plugin. This has happened.

So before touching published tags:

```bash
gh workflow disable Release --repo alex-roc/zotero-agent   # then push, then:
gh workflow enable  Release --repo alex-roc/zotero-agent
```

Afterwards check `updates.json` on `main`, and the release bodies for a duplicated
`**Full Changelog**` line. The XPI build is reproducible, so a re-uploaded asset
keeps its sha256 and `update_hash` stays valid.

Rewriting the **tap** leaves every already-cloned tap on an orphaned commit, so
`brew info` keeps reporting the old version until the user runs `brew update` —
which recovers on its own, because Homebrew hard-resets taps rather than merging.

GitHub's own caches lag behind a rewrite and the PyPI badge is a camo-cached
shields.io image, so neither a stale sidebar nor a stale badge means the history
is dirty — the REST API and `graphs/contributors-data` are the honest sources.

The contributors **sidebar** is a separate index. Renaming the default branch away
and back (`gh api repos/OWNER/REPO/branches/main/rename -f new_name=...`) forces it
to recompute; the second rename needs a retry, because GitHub reserves the old name
for redirects for a moment, and it can leave `default_branch` on the temporary name.
While the branch is renamed, `raw.githubusercontent.com/.../main/updates.json` 404s
— and that is the plugin's `update_url`, so keep the window to seconds.

The recompute is not instant. On the tap it landed immediately; on this repo, which has
merged PRs, it took about an hour — long enough to look like a failure. Wait before
escalating.

What does survive forever is `refs/pull/N/head`: the PRs' original commits still carry
the trailer and are still served at their old URLs, and no API can delete them. They no
longer feed the contributors sidebar, but a squash merge does not scrub them — the only
way to be rid of them is to never let the trailer reach a PR branch.

## Docs

- Three documents exist **twice** (`docs/` + `web/src/content/docs/`), and
  `tests/test_doc_parity.py` enforces it. A new fact about installing, updating or
  security goes into `SHARED_FACTS`, or one copy will go stale — this has happened.
- `docs/commands.md` and the site's `reference/commands.md` are **generated**. Never
  edit them by hand.
- `dev-docs/` and `marketing/` are **gitignored on purpose**: maintainer notes that
  never ship. Write there freely; it will not appear in a commit.

## Code

- The core stays **stdlib-only**. Anything heavier goes behind an optional extra
  (`[mcp]`, `[toc]`), reached through a single guard function.
- One version number covers the CLI *and* the plugin, sourced from
  `src/zotero_agent/__init__.py`; tests enforce every copy of it.

## Driving the bridge against itself

`zot restart` had to learn three things the hard way; they apply to anything else
that reaches through the endpoint to touch the plugin or the process hosting it:

- **Schedule, then reply.** Quitting or unloading inline kills the socket before
  the HTTP response leaves, so a success looks like a connection error. Hand the
  work to `Zotero.getMainWindow().setTimeout(..., 500)` and return immediately.
- **`Addon.reload()` resolves without reloading.** It leaves the plugin loaded and
  the old code answering. A real reload is `await addon.disable()` → pause →
  `await addon.enable()`, and it must run in the **window's** realm (`w.eval`):
  disabling the plugin unloads the very scope a callback would live in.
- **Verify with something only the new state can produce** — the reloaded plugin
  writing this run's nonce to a pref. "The endpoint answers" is also true of a
  plugin that never reloaded, and the endpoint class is reused across reloads, so
  neither is proof.
